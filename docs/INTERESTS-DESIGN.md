# 관심사 고르기 설계 (B 단계)

> 상태: 열린 질문 5개 모두 확정 (2026-10-17). 아직 만들지 않음.
> 근거: 직군별 조사 5건(데이터 사이언티스트·ML 엔지니어·FDE·LLM 앱·UI/UX 피드 관리) — 피드 약 300곳을 실제로 열어 확인한 결과.

## 0. 목표와 원칙

- 지금 브리핑은 "AI 코딩 에이전트를 쓰는 개발자" 한 종류만 위한 것이다. 이걸 **여러 관심사를 함께 고를 수 있게** 넓힌다.
- 원칙
  1. **수집은 넓게, 고르기는 브리핑에 넘길 때.** 같은 자료를 관심사에 따라 다르게 고를 수 있게 한다. (A 단계에서 이미 이렇게 바꿈)
  2. **정해진 흐름 위에서만 AI를 쓴다.** 사용자가 AI와 자유롭게 대화하며 방법을 찾게 하지 않는다. AI가 하는 일은 정해진 질문의 보기 만들기, 정해진 형식의 결과 내기뿐이다.
  3. **출처 목록은 앱이 챙긴다.** 사용자는 "무엇을 받을지"만 고르고, 고장 난 주소는 업데이트로 고쳐진다.
  4. **같은 소식은 카드 하나로 묶는다.** 관심사가 늘어도 소식이 겹쳐 보이지 않게 한다.

## 1. 관심사

| id | 이름 | 카드 태그 | 판별 규칙 | 핵심 |
|---|---|---|---|---|
| `ai-coding` | AI 코딩 에이전트 | AI 코딩 | `ai` | Claude Code·Codex 같은 도구의 새 기능·바뀐 기본값·혜택 (지금 기본) |
| `data-science` | 데이터 사이언스 | 데이터 | `data` | pandas·Polars·DuckDB·dbt 같은 라이브러리와 BigQuery·Databricks 같은 플랫폼의 변경·지원 종료·가격, 실험·인과 사례 |
| `ml-engineering` | ML 엔지니어링 | ML | `ml` | 보안 권고, vLLM·SGLang·PyTorch 릴리스, 오픈 웨이트 공개, GPU 비용 |
| `enterprise` | 엔터프라이즈 도입 (FDE) | 도입 | `ent` | 모델 단종·가격·리전, 엔터프라이즈 기능 GA, 국내 규제·클라우드, 장애 |
| `llm-apps` | LLM 앱·RAG | LLM 앱 | `rag` | LangChain 등 프레임워크, 벡터 DB, 임베딩·리랭커, 문서 파싱(HWP), 평가 |
| `custom-*` | 직접 만든 관심사 | 사용자가 정함 | 사용자 키워드 | 아래 4절 — 「AI 소식(일반)」도 이렇게 만든다 |

- 다섯 직군은 겹치는 부분이 있지만, 각 묶음의 고유한 출처가 50% 이상이라 따로 둔다.
  - 겹침이 가장 큰 쌍은 「엔터프라이즈 도입」과 「LLM 앱」(40~50%)이다. 둘 다 보안·MCP·클라우드 AI를 다룬다.
- 겹치는 피드는 **한 번만** 받는다.
- 조사 원문(검증된 피드 목록, 판별 규칙, 기준 문장)은 `local/research/interest-*.md`에 있다. 저장소에는 올리지 않는다.

## 2. 데이터 구조

### 2-1. `popme/feeds.toml` — 출처 정의는 여기 한 곳에만

```toml
[feed.codex-releases]          # id는 절대 바꾸지 않는다 (config·DB가 id로 가리킴)
name = "Codex 릴리스"
url = "https://github.com/openai/codex/releases.atom"
group = "공식 변경내역"         # 묶음 = 상한 단위, 화면에서 접히는 그룹
# type = "rss"                # 출처 모듈 종류 (없으면 rss) — 6-1
max_chars = 1500
skip = 'alpha|beta|-rc'
skip_note = "시험판(alpha·beta·rc)은 빼고 받아요"   # 화면에 보일 말
expect_days = 7                # 이 기간의 2배 동안 새 글이 없으면 '멈춤 의심'
via = "mirror"                 # 미러면 화면에 표시하고, 점검할 때 먼저 본다
old_names = ["Codex 릴리스"]    # DB items.source가 이름이던 시절과 맞춰 볼 때
old_urls = []
```

### 2-2. `popme/profiles/<id>.toml` — 관심사

```toml
id = "data-science"
name = "데이터 사이언스"
tag = "데이터"
summary = "pandas·SQL·실험·통계, 데이터 플랫폼 가격·변경"
order = 2
status = "ready"               # "draft"면 [news] drafts = true일 때만 보인다
criteria = """                 # 브리핑 AI에게 줄 「고르는 기준」 (직군 조사 초안)
- 쓰는 라이브러리·데이터 플랫폼의 메이저 버전·기본값 변경·EOL·가격·쿼터가 최우선 …
"""
discovery = "실험·통계·데이터 도구·LLM 분석 활용에 실질 정보를 주는 사람"   # 발굴 카드 기준
topic = "data"                 # 판별 규칙 이름 (popme/collectors/rss.py TOPICS)

[caps]                         # 묶음별 상한 (이 관심사 몫)
"공식 변경내역" = 20
"공식 발표" = 15

[[feeds]]
id = "duckdb-releases"
why = "DuckDB 메이저 버전·기본값 변경"

[[feeds]]
id = "geeknews"
filter = true                  # 이 피드는 이 관심사 글만 넘긴다 (topic으로 거름)
why = "한국 개발자들이 많이 본 데이터 글"

[[feeds]]
id = "arxiv-econ-em"
default = false                # 「더 볼 수 있는 출처」 — 직접 켜야 받는다
why = "계량경제 논문 (하루 0~1편만 브리핑에)"
```

- 판별 규칙(정규식)은 코드(`rss.TOPICS`)에 둔다. 규칙마다 오탐 예시 테스트가 있다.
  - 이미 있는 것: `ai`, `data`, `ml`
  - 더할 것: `ent`, `rag`
  - 직접 만든 관심사는 정규식 대신 **키워드 목록**을 쓴다 (4절).
- 피드가 여러 관심사에 겹칠 때
  - **filter**: 고른 관심사 중 하나라도 filter 없이 그 피드를 넣었으면 전부 받는다. 모두 filter면 그 관심사들의 판별 규칙 중 하나라도 맞는 글만 받는다. (지금의 `ai+data`를 일반화한 것)
  - **상한**: 관심사별 caps를 묶음마다 더한다. 그 위에 전체 상한을 둔다: 관심사 1개 140, 2개 200, 3개 이상 240.

### 2-3. `config.toml` — 사용자 몫만

```toml
[news]
interests = ["ai-coding", "data-science"]
off = ["xai-news"]                 # 끈 앱 출처
on  = ["arxiv-econ-em"]            # 기본은 꺼진 출처 중 켠 것
# drafts = true                    # 조사 중인 관심사도 보기 (개발자)

[news.tweak.codex-releases]        # 앱 출처 조정 (화면엔 "내가 바꾼 설정 있음"만)
skip = 'alpha|beta|-rc|nightly'

[[rss]]                            # 내가 더한 출처 (지금과 같은 형식)
name = "Example 블로그"
url = "https://example.com/feed.xml"
group = "실사용 검증"
interest = "data-science"          # 없으면 모든 관심사
filter = true
```

- `config.example.toml`(친구 zip 포함)에서는 `[[rss]]` 20개를 빼고 `[news] interests = []`와 설명만 둔다. 실제 값은 마법사가 채운다.
- 직접 만든 관심사는 개인 것이므로 `DATA_DIR/profiles/custom-*.toml`에 둔다. 공개 저장소에 섞이지 않는다.

### 2-4. 지금 설정 옮기기 (한 번만, 다시 돌려도 결과가 같게)

1. 조건: `[news]`가 없고 `[[rss]]`가 있을 때. 먼저 `config.toml.bak-날짜`로 백업한다.
2. `interests = ["ai-coding"]`로 둔다.
3. `[[rss]]`의 url을 정규화해서 feeds.toml의 `url`·`old_urls`와 맞춰 본다.
   - 맞으면 블록을 지운다. 이때 skip·max_chars가 앱 값과 다르면 `tweak`으로 남긴다.
   - 안 맞으면 「내가 더한 출처」로 그대로 둔다.
4. DB의 `items.source`는 **이름 그대로 둔다** (B1-2에서 정함 — 지난 글을 고쳐 쓰지 않아도 된다).
   - 대신 feeds.toml의 이름을 함부로 바꾸지 않는다. 그동안의 20곳은 예전 이름 그대로다. 이름이 겹치면 테스트가 막는다.
   - 꼭 바꿔야 하면 `old_names`로 예전 이름도 그 출처로 본다 (아직 쓰는 곳 없음).
   - `briefing.rss_items`는 이름으로 지금 받는 출처를 찾아 topic·skip·묶음을 쓴다. 안 받는 출처의 지난 글은 넘기지 않는다.
5. 다음 브리핑에서 한 번만 알린다 (B1-2는 문구를 `%LOCALAPPDATA%\POPME\news-migrated.txt`에 남기고, 보여 주는 건 B1-3). "소식 출처를 정리했어요: N곳은 이제 POPME가 챙기고, 내가 더한 M곳은 그대로예요. [출처 보기]"

## 3. 브리핑

### 3-1. 공통 카테고리 (8칸)

| 칸 | 들어갈 것 (직군 예) |
|---|---|
| 혜택·비용 | 크레딧·무료·가격 인하, GPU·인스턴스 가격 |
| 보안·장애 | CVE·프롬프트 인젝션·악성 패키지, API 장애 |
| 규제·정책 | AI 기본법·개인정보·망분리·공공 기준 |
| 업데이트·단종 | 라이브러리·플랫폼·API 변경, 지원 종료·은퇴, GA |
| 새 모델·도구 | 모델 출시(오픈 웨이트 포함), 새 오픈소스·도구 |
| 방법·흐름 | 기법·방법론·평가·에이전트 개발 방식 |
| 사례·커뮤니티 | 현업 적용기, 국내외 커뮤니티 반응 |
| 발굴 | 계속 지켜볼 만한 계정 |

- 화면의 필터 칩은 **그날 카드가 있는 칸만** 보여 준다. 좁은 패널이 붐비지 않게 하려는 것이다.
- 예전 브리핑의 카테고리(혜택·업데이트·흐름·오픈소스·커뮤니티)는 표시할 때 새 칸으로 바꿔 보여 준다. 저장된 자료는 그대로 둔다.

### 3-2. 카드 태그

- 카드 JSON에 `tags`를 더한다. 고른 관심사의 tag 중에서 0~2개를 넣는다. 만든 뒤 고른 관심사 목록에 있는 tag인지 검사한다.
- 화면에는 관심사를 **2개 이상** 골랐을 때만 태그를 보여 준다. 태그를 누르면 그 관심사 카드만 보이고, 분류 줄 끝에 "데이터만 보는 중 ✕"가 붙는다.
- 세부 꼬리표(단종·가격·GA·CVE·국내 LLM …)는 지금 있는 `chips` 칸을 그대로 쓴다.
- **관심사 태그 넣고 빼기** (사용자 요청): 마법사에서만이 아니라 **언제든** 관심사를 더하고 뺄 수 있다.
  - 브리핑 탭 위 태그 줄은 `[AI 코딩 ✕] [데이터 ✕] [+]` 모양이다.
    - ✕를 누르면 그 관심사를 뺀다. 되돌리기 토스트가 뜬다.
    - +를 누르면 관심사 목록과 「직접 만들기」가 나온다.
      (B1-3은 관심사 목록만. 「직접 만들기」는 B3에서 붙인다.) 관심사를 하나도 안 골랐으면 `[+ 관심사 고르기]`만 보인다.
  - 바꾼 내용은 `[news] interests`에 바로 저장한다. 출처 목록은 다음 수집부터 바뀐다.
  - **이미 만든 오늘 브리핑**: 뺀 관심사의 태그만 달린 카드는 접어서 "빼 둔 관심사 카드 N개"로 둔다. 다시 만들지는 않는다.
  - **카드 태그 고치기**는 상세 설정 안에 둔다(확정).
    - 「소식 출처」 화면의 상세 설정에서 「카드 태그 고치기」를 켜면, 펼친 카드에 `(데이터 ✕) [+태그]`가 보인다.
    - 고친 태그는 그 카드에만 저장한다(브리핑 JSON). 태그로 거르기에 바로 반영된다.
    - 고친 것을 배워서 다음 브리핑에 쓰지는 않는다(정해진 동작 원칙).
    - 기본은 꺼 둔다. 처음 쓰는 사람에게는 보이지 않는다.
    - B1-3에서는 `config.toml`의 `[news] card_tags = true`로 켠다. 「소식 출처」 화면의 켜기 버튼은 B2에서 붙인다.

### 3-3. 지시문

- `BRIEFING_RULES`의 「고르는 기준」을 관심사별 `criteria`를 이어 붙인 것으로 바꾼다. 공통 규칙(합치기·확인됨/미확인·제목 규칙)은 그대로 둔다.
- 「같은 소식은 여러 출처라도 카드 하나」 규칙을 더 강하게 쓴다. 조사에서 "오픈 모델 하나가 11곳에 동시에 실림"을 실제로 봤다.
- 발굴 기준도 관심사별 `discovery`를 이어 붙인다.

## 4. 관심사 설정 — 고르기·입력 → 문답 → 묶음 만들기 (2026-10-19 다시 정함)

예전 안(키워드 → 어떤 일·궁금한 것·피하고 싶은 소식 → 카탈로그 id로만 만들기)과 「AI 활용(일반)」 기본 관심사 안은 버렸다.
**어떤 분야든(축구·반도체·K-뷰티 …) 지금 「AI 코딩」과 같은 짜임의 출처 묶음을 만든다.**
이 흐름이 B1-4(마법사 관심사 단계)·B1-6(X 계정 관심사별)·B3(직접 만들기)를 하나로 묶는다.

### 4-1. 흐름

```
 ① 관심사 고르기                     [AI 코딩] [데이터] [ML] [도입] [LLM 앱]
                                   또는 [ 직접 입력: 축구                 ] [시작]
 ② 어디 소식을 볼까요?               (한국어만) (해외도)
 ③ 소식 받고 싶은 사람은?            해외 ☑ 펩 과르디올라 ☐ …   국내 ☑ 손흥민 …   [+ 직접 입력]
 ④ 소식 받고 싶은 기업은?            세계 ☑ 맨시티 …            국내 ☑ 대한축구협회 …   [+ 직접 입력]
 ⑤ 특히 궁금한 것은?                 [이적] [부상] [전술] [국가대표] …   (여러 개)
 ⑥ 이렇게 만들까요?
    사람  손흥민   뉴스 ✓   X ─ 로그인하면 이 사람 소식을 더 잘 받을 수 있어요 [X 로그인하기]
    기업  맨시티   X ✓ · 공식 뉴스 ✓ · 뉴스 ✓
    이런 소식을 골라요 ▾  · 이적·부상·감독 발언 …
                                                   [다시 고르기]  [만들기]
```

- **미리 만든 관심사(5개)를 골라도 같은 문답을 한다.** 단, 제가 골라 둔 사람·기업·세부 주제가 체크된 채로 나오고, 단계마다 「이대로」로 넘길 수 있다.
  처음 쓰는 사람도 「이대로」만 눌러 한 번에 끝낼 수 있게 한다.
- 관심사를 여러 개 고르면 관심사마다 ②~⑥을 차례로 한다. 미리 만든 관심사는 「이대로 모두」로 건너뛸 수 있다.
- ②를 앞에 두는 이유: 「한국어만」이면 ③④의 보기도 국내 사람·기업 위주로 만든다.
- 이 화면은 마법사의 「관심사」 단계이면서, 브리핑 탭 태그 줄의 `[+]`에서도 연다(설정 창 `#interests` 모드).

### 4-2. 받는 방법 — X·Threads가 중심, RSS가 받쳐 준다

| | X·Threads | 뉴스 검색 RSS | 공식 사이트 RSS |
|---|---|---|---|
| 담기는 것 | 본인이 하는 말 | 남이 전하는 소식 (이적·실적·사고) | 기업의 공식 발표 원문 |
| 받는 방식 | 전용 Chrome, 사람 속도, 한 번에 30계정까지 돌아가며 (6-3) | 주소만으로, 동시에 | 〃 |
| 필요한 것 | X 로그인 | 없음 | 없음 |

- 사람 = X·Threads 계정(확인된 것만) + 이름으로 뉴스 검색. 기업 = 공식 X 계정 + 공식 사이트 RSS(있으면) + 이름으로 뉴스 검색.
- 운동선수·연예인·경영인은 본인이 잘 안 올리고 궁금한 소식은 기사로 나온다. 그래서 뉴스 검색을 늘 같이 둔다.
- AI 코딩처럼 「사람 말은 X, 맞춰 보기는 RSS」 짜임이 그대로라 브리핑의 확인됨/미확인이 그대로 돈다.
- **X 로그인이 없으면 막지 않고 권한다:** 「로그인하면 이 사람 소식을 더 잘 받을 수 있어요 [X 로그인하기]」. 그동안은 뉴스로만 받는다.

### 4-3. 뉴스 검색

- **구글 뉴스 (기본, 키 없음):** `https://news.google.com/rss/search?q=<검색어>+when:2d&hl=ko&gl=KR&ceid=KR:ko`
  (해외는 `hl=en-US&gl=US&ceid=US:en`). 사람·기업마다 주소 하나, 지금 RSS 모듈로 받는다(조건부 요청 포함).
  - 2026-10-19 시험: 「손흥민」 2일 100건·언론사 54곳(연합뉴스·KBS·스포츠조선 …). 국내 주요 언론사가 잡힌다.
  - 한계: 문서화된 API가 아니라 바뀔 수 있고, 한 번에 100건까지. **스팸 언론사가 섞인다** —
    「삼성전자 HBM」 70건 중 37건이 「Calgary Roughnecks」. 제목 끝 「 - 언론사」로 거르는 목록과, 같은 기사 합치기를 둔다.
- **네이버 뉴스 (선택, 키 필요):** 상세 설정의 「네이버 뉴스를 더 잘 받고 싶어요」에서 켠다.
  - 2026-07-31부터 개발자센터(developers.naver.com)는 새 키 발급을 하지 않는다. **NAVER API HUB(네이버 클라우드)**에서 받는다.
    기존 개발자센터 키는 2027-06-30까지만 된다.
  - 요금: 한시적 무료(유료로 바꿀 때 미리 공지, 쓴 만큼 내는 방식), 무료 기간 한도 월 775,000건. POPME는 한 달 수백 건.
  - 가입할 때 결제수단을 요구하지 않는다 (2026-10-19 사용자가 직접 확인).
  - 새 출처 모듈 `sources/naver.py` (헤더 `X-NCP-APIGW-API-KEY-ID`·`X-NCP-APIGW-API-KEY`). 키는 `config.toml [naver]`.
  - **단계별 안내** (메일 앱 비밀번호와 같은 방식):
    ```
    네이버 뉴스를 더 잘 받고 싶어요 ▾
     ⓘ 네이버 검색 키가 필요해요. 지금은 무료이고, 유료로 바뀌면 네이버가 미리 알려 줘요.
     1. 네이버 클라우드에 가입·로그인해요                 [사이트 열기]
     2. 콘솔 › Services › NAVER API HUB › 이용 신청        [바로 열기]
     3. Application 등록 → 쓸 API에서 「뉴스 검색」만 체크
     4. Client ID와 Client Secret을 복사해요 → [복사한 값 넣기]  (채팅에는 붙이지 마세요)
     5. [확인하기] → 「손흥민」으로 시험 검색 → ✓ 기사 10건을 받았어요
    ```
    5에서 실패하면 원인별로 안내한다 (키가 틀림 / 뉴스 검색 체크 안 함 / 한도 초과).
- 키 없이 전용 Chrome으로 네이버 검색 화면을 읽는 방법은 쓰지 않는다 (느리고 자동 접근으로 막힐 수 있음).

### 4-4. AI가 하는 일과 확인

- AI(설정의 브리핑 AI, 도구 끔)가 만드는 것: ③④의 사람·기업 후보(이름·한 줄 이유), ⑤의 세부 주제, ⑥의 고르는 기준 문장·판별 단어.
  정해진 JSON으로 받고 길이·개수를 검사한다. 판별 단어는 단어 목록만 받고 코드가 안전한 정규식으로 바꾼다.
- **AI가 말한 계정·주소는 그대로 믿지 않는다.**
  - X·Threads: 수집기로 실제로 열어 계정이 있고 최근 글이 있는지 본다 (로그인 필요 — 없으면 4-2의 권하는 문구).
  - 공식 사이트 RSS: 정해진 규칙으로 찾는다 (`<link rel=alternate>` → `/feed` → `/rss.xml`) → 열어서 최근 글이 보이는 것만.
  - 뉴스 검색어: 코드가 이름으로 만든다 (동명이인이 많으면 ⑤의 세부 주제를 붙여 좁힌다).
- 카탈로그(`popme/feeds.toml`, 제가 미리 확인한 출처) 밖 출처도 쓸 수 있다. 단 위 규칙으로 확인된 것만.
- AI가 실패하면 「AI가 지금 답하지 못했어요」 → ③④는 직접 입력만, ⑤는 건너뛰고 만든다.

### 4-5. 저장

- 새로 만든 관심사: `DATA_DIR/profiles/custom-<id>.toml`. 출처는 id가 아니라 정의째로(이름·주소·묶음) 담는다.
- 사람·기업은 관심사 파일에 둔다:
  ```toml
  [[people]]
  name = "손흥민"
  region = "kr"
  x = "Sonny7"            # 확인된 것만 (없으면 비움)
  news = "손흥민"          # 뉴스 검색어
  [[companies]]
  name = "맨체스터 시티"
  x = "ManCity"
  feeds = ["https://…"]   # 확인된 공식 RSS
  news = '"맨시티" OR "맨체스터 시티"'
  ```
- 미리 만든 관심사(5개)에도 `[[people]]`·`[[companies]]`를 더한다 (B1-6의 「관심사별 X 계정」이 이것). 사용자가 문답에서 고친 것은 `config.toml [news.picks.<관심사>]`에 사용자 몫만 남긴다.

## 5. 화면

1. **마법사 「관심사」 단계** = 4장의 관심사 설정 화면 (메일 다음, 로그인 앞). 0개면 「다음」이 꺼진다. 2개 이상이면 "겹치는 N곳은 한 번만 받아요"를 보여 준다.
2. **「소식 출처」 화면** (설정 창을 `#sources` 모드로 다시 씀. 트레이·마법사 링크·브리핑 탭 아래에서 연다)
   - 관심사 칩, 묶음별로 접히는 목록. 줄마다 스위치, 이름, 관심사, 마지막 새 글이 보인다.
   - 줄을 펼치면 「왜 넣었나요」, 「이렇게 받아요」(skip_note), 최근 글 3개, 주소가 보인다.
   - 그 밖의 칸: 「더 볼 수 있는 출처」, 「끈 출처」(언제·어디서 껐는지), 「내가 더한 출처」, 「출처 더하기」
3. **패널 브리핑 탭**
   - 카드를 펼치면 "출처: …"와 `[⋯]` 메뉴가 나온다. 메뉴에서 「○○ 그만 보기」를 고르면 되돌리기 토스트가 뜬다. 공식 변경내역은 한 번 더 확인한다.
   - 관심사 태그로 거를 수 있다.
   - 맨 아래에 "출처 N곳에서 모았어요 · 1곳이 며칠째 열리지 않아요 · 출처 관리"가 보인다.
   - 학습형 "관심 없음"은 넣지 않는다(정해진 동작만 둔다는 원칙).

## 6. 수집

### 6-1. 출처 모듈 — RSS도 모듈 중 하나

지금은 RSS(`collectors/rss.py`)가 `jobs.py`·`briefing.py`에 직접 엮여 있다. 출처 종류가 늘어나므로(보안 권고·단종 감지·HF), **같은 규격의 모듈**로 나눈다.

```
popme/sources/
  __init__.py      # 모듈 등록표 KINDS = {"rss": rss, "advisory": advisory, "pagediff": pagediff, "hf": hf}
  base.py          # 공통 규격: Item, Source, 결과·오류 형식
  rss.py           # 지금 collectors/rss.py에서 옮김 (fetch·skip·gzip)
  advisory.py      # GitHub Advisory API (B4)
  pagediff.py      # 단종 페이지 바뀐 부분 (B1)
  hf.py            # HF daily papers·trending (B4)
popme/topics.py    # 판별 규칙 TOPICS(ai·data·ml·ent·rag) + 키워드 목록 → 정규식 (직접 만든 관심사용)
popme/catalog.py   # feeds.toml·profiles 읽기, config [news]와 합쳐 「지금 받을 출처」 계산, 옮기기
```

- **모듈 규격** (`base.py`)
  - `fetch(feed: dict) -> list[Item]` (상태가 필요한 모듈은 B1-5 pagediff에서 `state`를 더한다)
    - `feed`: feeds.toml의 한 항목에 tweak을 반영한 것
    - `state`: 모듈이 다음 실행 때 쓸 값. 예: pagediff의 이전 해시, advisory의 마지막 id
  - `Item` = `{feed_id, url, title, summary, published, extra}`. DB `items`에 그대로 들어간다(`source`는 feed id).
  - 실패하면 예외를 던진다. 거르기·태그·상한은 모듈이 하지 않는다. 그건 공통 단계(`catalog`·`briefing`)의 일이다.
  - 모듈마다 `describe(feed) -> str`을 둔다. 「소식 출처」 화면의 "이렇게 받아요" 문구로 쓴다.
- **수집 흐름:** `catalog.active_feeds(cfg)` → URL이 같으면 하나로 합침 → kind별 모듈로 8개씩 동시에 받음 → `db.upsert_items` → 피드 상태 기록
- **X·Threads:** 로그인한 전용 Chrome이 필요하고 흐름이 달라서 이번에는 그대로 둔다. 다만 같은 `Item`·피드 상태 규격으로 맞춰 둬서, 나중에 관심사별 계정을 묶을 수 있게 한다(열린 질문 5).
- **새 출처 종류 더하기** = `sources/`에 파일 하나 + `KINDS`에 한 줄 + feeds.toml에 `type = "…"` 항목. 거르기·태그·화면은 그대로 따라온다.

### 6-3. X 계정도 관심사별로 (확정)

- profile에 `[[x]]`를 둔다: `handle`, `why`. 관심사마다 **확인된 계정** 5~10개.
  - 확인은 X 수집기로 실제로 열어서 한다. 조사의 후보 계정은 아직 확인하지 않았으므로 B1 작업에 포함한다.
- 받을 X 계정 = 사용자 핵심 계정(`[x] accounts`) + 고른 관심사들의 `[[x]]`. 이름이 같으면 하나로 합친다.
  - 「소식 출처」 화면에서 끄고 켤 수 있다. 피드와 같은 `off`·`on` 목록에 `x:handle`로 둔다.
- **수집 시간·위험 관리**
  - X 계정이 30개를 넘으면 한 번에 다 보지 않는다. **마지막으로 본 지 오래된 계정부터** 30개만 보고, 나머지는 다음 수집에 돌아가며 본다.
  - 사람 속도(페이지 사이 4~9초)는 그대로 둔다. 하루 수집 시간이 관심사 수에 따라 늘지 않게 하려는 것이다.
- 발굴(새 계정 찾기)의 기준도 고른 관심사별 `discovery` 문장을 합친 것으로 바꾼다.

### 6-2. 받기

- **동시에 받기:** 피드가 100곳을 넘을 수 있다. 지금은 순서대로 받고 하나에 20초까지 기다린다. URL이 같으면 하나로 합치고, 8개씩 동시에 받는다. 꺼진 출처는 받지 않는다.
- **피드 상태:** 피드마다 마지막 성공 시각과 마지막 새 글 시각을 DB에 둔다. 「소식 출처」 화면과 주간 점검이 이것을 쓴다.
- **주간 점검:** GitHub Actions에서 `tools/check_feeds.py`가 열리지 않는 피드와 `expect_days`의 2배 동안 새 글이 없는 피드를 issue로 올린다.
  - 앱 출처가 고장 나면 친구에게는 3일째부터 "업데이트 때 고쳐져요"만 보인다.
  - 브리핑 「수집 경고」에는 내가 더한 출처만 넣는다.

| 수집기 | 필요한 관심사 | 방법 | 확인 |
|---|---|---|---|
| 보안 권고 | ML·LLM 앱·도입 | GitHub Advisory API (`ecosystem=pip&affects=…`), high·critical만 | 열리는 것 확인 |

- 셋 다 피드처럼 feeds.toml에 `type = "advisory" | "pagediff" | "hf"`로 넣는다. 관심사가 id로 가리키게 해서 끄고 켜는 화면을 같이 쓴다.

## 9. 위험

| 위험 | 대응 |
|---|---|
| 친구가 업데이트를 안 받아 앱 출처 개선이 안 퍼짐 | "새 버전이 있어요" 말풍선 (원격 feeds.toml은 v1에서 하지 않음) |

## 10. 정해진 것 / 열린 질문

**정해진 것 (사용자 결정)**
